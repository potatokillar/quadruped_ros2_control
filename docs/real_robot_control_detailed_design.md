# 四足运控新版本与真机接入详细设计

## 1. 文档目的

本文整理新版本四足运动控制项目及真机接入方案中已经讨论并确认的设计结论，同时记录尚未确定的事项。

当前阶段仅进行设计，不开展代码拆分、硬件接入或算法修改。后续实现时，应以本文中“已确认”的内容为约束；“待讨论”内容不能直接作为实现依据。

## 2. 项目范围与基本原则

### 2.1 项目定位

- 新仓库暂定名为 `iiri_quadruped_control`，作为新版本四足运动控制项目。
- `iiri` 仅是公司或项目编号，不应出现在代码包名、类名、命名空间或业务类型名称中。
- 第一阶段只支持小狗，不同时设计多种新机型。
- 机器人类型固定使用：
  - `quadruped_small`
  - `quadruped_middle`

### 2.2 当前阶段约束

- 暂时不拆分当前仓库，也不删除当前仓库中的文件。
- 在真机接入完成并经过仿真验证前，保留现有项目组织与运行方式。
- 算法层和硬件、设备、系统状态管理层必须保持边界清晰，不能相互混杂。
- 尽量不修改现有运控算法逻辑，尤其不能随意修改 MPC 和 WBC 的数学模型、求解流程与控制逻辑。
- 后续实现必须增加必要注释，说明坐标变换、时间戳语义、安全状态转换和参数来源。

## 3. 总体架构

### 3.1 分层设计

新版本最终应形成以下逻辑分层：

1. 算法层
   - 保留现有 `ocs2_quadruped_controller` 以及 MPC、WBC、状态估计等核心逻辑。
   - 使用统一的关节状态、机身状态和规划接触状态。
   - 输出统一的关节控制命令。

2. 硬件抽象层
   - 对算法层提供一致的关节状态接口、IMU 状态接口和关节命令接口。
   - Gazebo 与真实机器人使用相同的 `ros2_control` 接口语义。
   - 仿真和真机的区别限制在硬件插件、设备驱动及配置层。

3. 设备驱动层
   - 电机和 IMU 的接入重新设计，不直接复制 `qr_wl` 中现有的设备组织方式。
   - 驱动层负责通信、协议解析、时间戳、在线检测和原始数据合法性检查。
   - 驱动层不包含 MPC、WBC 或步态逻辑。

4. 安全与状态管理层
   - 统一管理启动、Idle、阻尼、正常控制、故障、急停和摔倒恢复。
   - 硬件故障状态与机器人姿态状态相互独立。

5. 配置层
   - 保存机器人类型、电机组合、关节映射、方向、限幅、超时与安全参数。
   - 机器人实例差异通过 TOML 配置表达，不写死在算法中。

### 3.2 数据流

```text
电机反馈 ─┐
          ├─> 硬件抽象/时间对齐 ─> 算法状态输入 ─> 状态估计 ─> MPC/WBC
IMU反馈 ──┘                                               │
                                                         v
                                              统一关节控制命令
                                                         │
                                                         v
                                                  电机硬件输出
```

仿真和真机都应遵循该数据流。算法层不应根据数据来自 Gazebo 还是真机而使用不同的 MPC/WBC 逻辑。

## 4. 关节命名与电机配置

### 4.1 统一关节命名

硬件层、配置层和算法接口统一使用算法层现有命名，放弃 `abad/hip/knee` 这套旧命名：

```text
FL_hip_joint
FL_thigh_joint
FL_calf_joint
FR_hip_joint
FR_thigh_joint
FR_calf_joint
RL_hip_joint
RL_thigh_joint
RL_calf_joint
RR_hip_joint
RR_thigh_joint
RR_calf_joint
```

底层协议中的腿编号和电机 ID 必须通过显式映射转换，不能依赖数组顺序隐式对应。

### 4.2 电机型号编码

电机编码由独立工具 `/home/wl/workspace/motor_code_tool` 管理。当前已存在：

- `M001`：Haitai `8108-j6`，MIT 协议，减速比 6。
- `M002`：Haitai `8108-j9`，MIT 协议，减速比 9。

电机编码用于反查厂家、型号、硬件版本、协议、减速比及后续补充的电机参数。编码应稳定且支持扩展，不把详细电机参数重复写入每个机器人配置。

### 4.3 小狗电机组合

小狗每条腿采用 6-6-9 组合：

| 关节位置 | 电机编码 |
| --- | --- |
| `hip_joint` | `M001` |
| `thigh_joint` | `M001` |
| `calf_joint` | `M002` |

TOML 文件命名规则为：

```text
<robot_type>_<motor_code>x<单腿数量>[_<motor_code>x<单腿数量>...].toml
```

当前小狗配置文件名应为：

```text
quadruped_small_M001x2_M002x1.toml
```

文件名只表达单腿电机组成；TOML 内部仍需通过 `motor_layout` 明确每个关节位置与电机编码的对应关系。

### 4.4 电机方向与软件零点

12 个关节当前统一确认：

```toml
direction = -1
```

算法坐标与电机原始坐标的转换为：

```text
q_algorithm = -(q_raw - q_zero)
q_raw_command = q_zero - q_algorithm_command
qd_algorithm = -qd_raw
tau_algorithm = -tau_raw
```

软件零点不采用零散、逐关节即时生效的方式。启动时应在全部 12 个电机已经使能、在线且反馈有效后，原子地建立一份完整的 12 关节零点快照。

## 5. 电机系统设计

### 5.1 已验证的启动顺序

真机启动顺序继续保持 `qr_wl` 中已经验证过的实际顺序：

1. 初始化电机通信。
2. 向电机发送使能命令。
3. 确认全部 12 个电机在线且反馈有效。
4. 读取当前关节位置。
5. 原子建立 12 关节软件零点。
6. 进入 `Idle`，保持零输出。
7. 完成 IMU 初始化和算法初始化。
8. 收到明确的控制请求后，才允许进入后续站立或控制流程。

机器人此时趴在地面，建立零点阶段不需要使用阻尼；零点建立完成后、算法启动前保持 `Idle`。

### 5.2 电机输出模式

电机侧至少需要以下模式：

- `Initializing`
  - 通信建立、电机使能、在线确认和软件零点建立阶段。
- `Idle`
  - 零输出：`kp = 0`、`kd = 0`、`tau_ff = 0`。
- `Damping`
  - 纯阻尼，只抑制速度。
  - `kp = 0`、`qd_des = 0`、`tau_ff = 0`，仅配置 `kd`。
  - 不保持故障发生时的位置。
- `Control`
  - 接收算法输出，并在安全限制后发送给电机。

### 5.3 在线检测与超时

- 电机通信与控制频率为 500 Hz。
- 每个电机独立维护最后有效反馈时间。
- 电机反馈超时阈值保持 300 ms。
- 控制循环运行时同步检测电机是否在线。
- 任一必要电机发生严重故障时，系统进入 `Error`，在线电机进入纯阻尼。
- 对于已经离线的电机，软件不能假定其能够接收到阻尼命令。

### 5.4 故障清除与急停

- 普通电机故障允许在条件满足时自动清除具体故障原因。
- 清除故障原因不等于自动恢复运动控制。
- 故障清除后只允许回到安全阻尼状态，不能自动恢复故障前的 `Control`。
- 软件急停采用纯阻尼，并且必须锁存。
- 急停解除后也不能直接恢复旧控制命令。

## 6. IMU 接入设计

### 6.1 设备信息

- 厂家：维特智能（WITMOTION）。
- 型号：当前认为是 JY901，实机接入前仍应核对设备标签或协议版本。
- 设备路径：`/dev/serial0`。
- 频率：约 200 Hz。
- 四元数存储顺序：`[w, x, y, z]`。

### 6.2 安装方向与坐标系

IMU 安装方向：

```text
               +X（向前/狗头）
                    ↑
                    |
   +Y（向左）  ←  机器人
                    |
                    ↓
               -X（向后/狗尾）
```

结合当前机器人 URDF 和算法坐标约定，机身坐标系也是：

- `+X` 向前。
- `+Y` 向左。
- `+Z` 向上。

因此 IMU 坐标系到机身坐标系的轴向旋转当前采用单位旋转。URDF 中 IMU 的实际安装位置偏移应后续核对，但不影响当前轴向结论。

### 6.3 四元数方向

JY901 输出四元数按机身坐标系到世界坐标系理解：

```text
q_WB = [w, x, y, z]
v_world = R(q_WB) * v_body
```

世界向量转换到机身坐标系时：

```text
v_body = R(q_WB)^T * v_world
       = R(q_WB^-1) * v_world
```

对于已归一化四元数：

```text
q_BW = q_WB^-1 = [w, -x, -y, -z]
```

算法中的重力投影应明确使用上述方向，不通过试错交换四元数分量或符号。

### 6.4 加速度语义

静止实测示例：

```text
ACC ≈ [-0.23, +0.52, +9.77] m/s²
```

这说明 IMU 输出的是包含重力支撑项的比力，静止且水平时机身 Z 轴约为 `+g`。状态估计中的世界系线加速度转换应保持：

```text
a_world = R_WB * a_specific_body + [0, 0, -g]
```

不能在驱动层直接把静止加速度强制清零，也不能重复扣除重力。

### 6.5 IMU 启动初始化

启动时机器人保证不会移动，因此不设计复杂的静止检测器。

初始化流程：

1. 电机保持 `Idle` 零输出。
2. 连续采集约 1 秒，即约 200 个完整有效 IMU 样本。
3. 对样本进行完整性和基本合理性检查：
   - 数据帧完整。
   - 不包含 NaN 或 Inf。
   - 四元数模长合理并执行归一化。
   - 数值没有明显越界。
4. 使用样本均值计算启动陀螺仪零偏。
5. 根据姿态下的理论比力计算启动加速度计零偏：

```text
expected_specific_force_body = R_WB^T * [0, 0, +g]
accel_bias = mean(raw_accel) - expected_specific_force_body
```

6. 运行期间分别扣除启动时计算的陀螺仪和加速度计零偏。
7. 保留真实的重力参考 roll、pitch，仅将初始 yaw 作为零航向。
8. yaw 归零使用四元数偏置变换，不使用欧拉角直接相减。
9. 初始化成功后才允许初始化算法并进入后续控制流程。

启动零偏本阶段按单次上电会话固定使用，不进行在线学习，以免把机器人真实运动误学习为偏置。

### 6.6 IMU 超时和短时丢帧

- IMU 真正故障阈值为 1 秒。
- 小于 1 秒的短时传输中断：
  - 继续使用最后一个有效姿态样本。
  - 系统可以保持 `Control`。
  - 必须保留 IMU 样本时间戳和数据年龄。
  - 状态估计器不得把同一个旧陀螺仪样本当作多个新样本反复积分。
- 连续 1 秒没有完整有效 IMU 数据：
  - 设置 IMU 故障。
  - 系统进入 `Error`。
  - 电机进入纯阻尼。

### 6.7 IMU 故障恢复

- IMU 恢复后，必须连续稳定接收 200 ms 的正常数据，才清除 IMU 这一具体故障原因。
- 200 ms 按实际接收时间判断，而不是写死为 40 帧；正常 200 Hz 下约为 40 个完整样本。
- 恢复确认期间电机继续保持纯阻尼。
- 中间再次出现无效数据或中断时，恢复计时重新开始。
- 清除 IMU 故障原因后，系统仍不能恢复旧的运动命令。

建议配置语义：

```toml
[imu.health]
fault_timeout_ms = 1000
recovery_stable_ms = 200
```

## 7. 多频率数据统一

### 7.1 频率关系

- 电机通信与控制循环：500 Hz。
- IMU 数据：200 Hz。
- MPC 以其现有规划频率运行。

不能要求不同设备在同一时刻产生数据，也不能为了组成单个快照而阻塞 500 Hz 电机循环等待新 IMU。

### 7.2 `StateSnapshot` 设计

`StateSnapshot` 是控制周期读取到的一组一致视图，不代表所有传感器具有完全相同的采样时刻。

每类数据必须独立保存：

- 设备样本值。
- 单调时钟时间戳。
- 样本序列号。
- 当前数据年龄。
- 有效性和健康状态。

500 Hz 控制周期读取：

- 最新的完整电机反馈。
- 最新的完整 IMU 样本。

当两个相邻控制周期之间没有新 IMU 数据时，采用最新值保持，但算法可以通过 IMU 序列号和时间戳判断该样本是否更新。驱动线程不得直接修改算法正在读取的对象，应通过实时安全缓冲区发布完整快照。

IMU 时间戳初期可使用主机 `steady_clock` 在完整组合帧形成时记录；是否进一步估计设备实际采样时刻，属于待验证项。

## 8. 无足端力传感器方案

### 8.1 算法是否必须依赖足端力

当前 MPC 和 WBC 的核心逻辑需要接触状态，但不等同于必须安装足端力传感器：

- MPC 本身已经规划每条腿的支撑和摆动时序。
- WBC 根据规划接触状态建立约束和任务。
- 足端位置和速度可由关节位置、关节速度、正运动学和雅可比矩阵计算。

因此，在不处理复杂地形且没有足端力传感器的阶段，可以运行现有算法。

### 8.2 状态估计调整

当前 `LinearKalman` 中用于判断支撑腿的 `foot_force` 输入，真机无足端力传感器时改为使用规划接触状态。

需要明确：

- 规划接触状态来自步态/MPC 的期望接触序列。
- 它表示“算法认为这条腿当前应该支撑”，不是传感器对真实接触的测量。
- 规划接触状态只用于选择或调整状态估计观测的可信度。
- 足端高度和足端速度仍由运动学计算，不能省略。
- 不修改 MPC/WBC 的核心数学逻辑。

这种方案适用于平地和简单地形，但无法直接识别踩空、提前触地、打滑或真实接触与规划不一致。未来增加足端力时，可将真实接触观测用于修正规划接触置信度，而不是删除规划接触状态。

## 9. 系统状态、安全状态与恢复

### 9.1 独立状态维度

必须区分：

1. 系统健康状态
   - `Normal`
   - `Error`
   - `EStop`

2. 机器人姿态状态
   - 正常姿态
   - `Fall`，表示真实摔倒
   - `Recovery`

硬件或 IMU 故障会令系统进入 `Error`，但不能因此直接把姿态标记为 `Fall`。只有摔倒检测器能够设置真实摔倒状态。

当 IMU 数据无效或过旧时，不允许使用陈旧姿态产生新的摔倒判断。

### 9.2 从故障退出

确认的安全恢复流程：

```text
Error
  ↓ 所有故障原因清除，IMU 已连续稳定 200 ms
Damping
  ↓ 操作者发出新的恢复命令
检查真实摔倒状态
  ├─ 未摔倒 → Idle → 重新初始化状态估计器 → Stand
  └─ 已摔倒 → Recovery → Stand
                                      ↓
                              等待新的运动命令
```

约束如下：

- `Error` 清除后只进入纯阻尼，禁止自动站立。
- 必须收到新的人工恢复命令。
- 清空故障前的速度命令、MPC 轨迹、控制输出和其他运动意图。
- 未真实摔倒时不执行翻身恢复动作。
- 真实摔倒时才进入 `Recovery`。
- `Stand` 完成后保持站立，不能自动恢复故障前的行走命令。
- 恢复过程中再次出现电机、IMU 或急停故障时，立即返回 `Error/Damping`。
- 自动恢复能力可作为后续功能，但真机调试阶段默认关闭。

## 10. 摔倒检测现状与设计方向

### 10.1 `qr_wl` 当前实现

`qr_wl` 的物理摔倒判定本质上使用四元数计算重力方向在机身坐标系中的投影：

```text
gravity_body = R(q_WB)^T * [0, 0, -1]
```

当前代码只在 `walk`、`stand`、`upright`、`handStand` 状态检查，并使用：

```text
gravity_body.z >= 0.5
```

直立时 `gravity_body.z` 约为 `-1`，倒扣时约为 `+1`。该阈值大约只会在机身倾斜超过 120°后触发，侧躺时 Z 分量约为 0，因此不能覆盖常见侧摔。

当前实现还存在：

- 单帧触发，没有持续时间。
- 没有进入和退出滞回。
- 摔倒方向仅根据重力投影 Y 分量判断。
- 硬件错误和 IMU 错误也会被直接切到算法 `fall` 状态，混淆了故障阻尼与真实摔倒。

### 10.2 已确认方向

- 可以继续使用四元数重力投影作为摔倒检测的主要依据。
- 新设计必须将真实 `Fall` 与 `Error` 分开。
- 不能沿用当前 `gravity_body.z >= 0.5` 作为完整摔倒检测规则。

### 10.3 待讨论

以下内容尚未确定：

- 采用重力投影 Z 分量、机身 Z 轴与世界 Z 轴夹角，还是同时结合投影 X/Y 分量。
- 侧摔、前摔、后摔和倒扣的具体阈值。
- 摔倒条件需要持续多久才生效。
- 是否设置进入阈值与退出阈值的滞回。
- 是否仅依赖姿态，或辅助使用角速度和估计机身高度。
- 哪些运动状态启用摔倒检测。
- `Recovery` 如何根据摔倒方向选择恢复动作。

## 11. 实时线程与优先级

优先级的设计顺序暂定为：

```text
急停与安全处理
  > 电机通信/控制 500 Hz
  > ros2_control 与 WBC 500 Hz
  > IMU 接收 200 Hz
  > MPC
  > 日志、监控和非实时业务
```

不能直接复制 `qr_wl` 的实时优先级数字。以下事项需要在目标机实测后确定：

- 各线程的具体实时优先级。
- CPU 亲和性。
- 电机 SPI 通信是否与 `ros2_control` 更新循环同线程。
- SPI 单周期最坏耗时和抖动。
- MPC 对 500 Hz 控制线程的影响。
- 日志和 ROS 通信的非实时隔离方式。

## 14. 实施边界

在上述待讨论事项得到确认前：

- 不拆分当前项目。
- 不修改 MPC 或 WBC 核心逻辑。
- 不开始实现真实电机和 IMU 驱动。
- 不将 `qr_wl` 中的故障即 `fall` 逻辑直接迁移到新项目。
- 不默认启用自动故障恢复、自动站立或自动翻身。
